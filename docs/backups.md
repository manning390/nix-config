# Homelab backups

Glaciem uses Restic to create encrypted, compressed, and deduplicated backups.

| Setting | Configuration |
| --- | --- |
| Local schedule | Daily at 05:00, with up to 15 minutes of jitter |
| Repository | `/backups/restic/glaciem` |
| Retention | 7 daily, 4 weekly, and 6 monthly snapshots |
| Included data | `/fast`, `/bulk`, `/home`, `/persist`, `/etc`, and `/var/lib` |
| Integrity checks | Metadata after each backup; a random 5% of stored data on Sundays at 12:00, with up to 15 minutes of jitter |
| Optional off-site copy | Daily at 06:00, with up to 15 minutes of jitter |

Retention buckets share unchanged data; they are not full independent copies.
Unreferenced data is pruned after successful backups. The two storage tiers are captured directly, so `/merged` is not backed up again. `/backups`, `/nix/store`, caches outside the included paths, and `/var/log` are not sources.

Applications, Samba, and DNS are briefly interrupted while consistent ZFS snapshots are taken. Services restart before Restic uploads the data; see [how snapshots work](#how-snapshots-work) for details.

Snapshots keep blocks changed/deleted during a backup alive until the job finishes; allow space for this, especially during the initial large backup.
Already compressed media usually does not shrink much. `/bulk` and `/backups` currently share the same physical HDD: off-site storage or another disk is needed to survive loss of that disk.

## Password setup with sops-nix

Glaciem reads the `restic_password` secret from `secrets/secrets.yaml` through sops-nix.
The decrypted password is available only to root at `/run/secrets/restic_password`; it is not generated by the backup service or stored in plaintext in the Nix store.

Before deploying, edit the encrypted secrets file:

```sh
sops secrets/secrets.yaml
```

Add a top-level `restic_password` value containing a strong password from your password manager.
If a backup repository has already been initialized, use its **existing password**.
With the previous generated-password configuration, that password is at `/var/lib/restic/homelab-password` on Glaciem.
Changing the file's contents does not change the password accepted by an existing Restic repository.

Glaciem's configuration declares the secret and selects it for Restic:

```nix
sops.secrets.restic_password = {
  owner = "root";
  mode = "0400";
};
homelab.backups = {
  generatePassword = false;
  passwordFile = config.sops.secrets.restic_password.path;
};
```

Keep an independent recovery copy of the password, or ensure you can decrypt the SOPS file without relying on Glaciem's disks.
An encrypted backup cannot recover its own missing password.
Other hosts can still opt into automatic password generation through `homelab.backups.generatePassword`.

## First backup

After adding the secret and deploying the configuration, run these commands **on Glaciem**:

1. Start the backup without waiting for the job to finish:

   ```sh
   sudo systemctl start --no-block restic-backups-homelab.service
   ```

   The first run initializes the repository using the sops-managed password.

2. Watch progress:

   ```sh
   sudo journalctl -u restic-backups-homelab.service -f
   ```

   Once the job finishes, press **Ctrl-C** to stop following the journal. This
   exits the log viewer without stopping the backup service.

3. List the completed backup snapshots and scheduled jobs:

   ```sh
   sudo restic-homelab snapshots
   systemctl list-timers 'restic-backups-homelab*'
   ```

## How snapshots work

Before each local backup, the job briefly stops active application writers, Samba, Pi-hole, PostgreSQL, and Redis, then takes ZFS snapshots named `restic-homelab`.
Snapshots are created in one transaction per pool because ZFS cannot snapshot multiple pools in a single command. Writers remain stopped until all pools have been captured.
It restarts those services before Restic reads the snapshots.
This captures databases in a cleanly stopped state alongside application files, with a short interruption to DNS and SMB. ZFS snapshots are removed when the local backup job exits, including on failure.

The backup service requires the storage mounts, verifies source dataset identities, and runs with reduced CPU/I/O priority. Only services that were active are restarted.
Errors appear in the systemd journal and mark the backup unit failed.
After a power loss during preparation, normal boot starts applications; the next backup removes leftover snapshots.

### Snapshot preparation fails with “multiple snapshots of same fs not allowed”

The original snapshot hook passed datasets from multiple pools to one `zfs snapshot`
command. ZFS rejects this with the misleading error above, before Restic starts.
Deploy the updated configuration, which groups snapshot creation by pool, then retry:

```sh
sudo systemctl start --no-block restic-backups-homelab.service
sudo journalctl -u restic-backups-homelab.service -f
```

The failure hooks resume the services stopped for snapshot creation and remove any
backup snapshots. No manual snapshot deletion or repository reset is needed.

## Adding a service to backups

Each enabled service module contributes its own units and local database dependencies to `homelab.backups.quiesceServices`.
Nix merges these contributions and removes duplicates, so multiple applications can declare a shared database.
To **quiesce** means to pause writes long enough to capture a consistent snapshot;
here the units are stopped briefly and restarted before the backup is read.
For example, a service module can declare this inside its enabled configuration:

```nix
homelab.backups.quiesceServices = ["my-app.service"];
```

Hosts can also contribute additional writers. Adding a unit only pauses its writes;
its data is captured only if its storage is covered by `sources`.
Child ZFS datasets are not included in parent snapshots; add them to `sources`.

## Optional off-site copy

The off-site job copies completed local Restic snapshots rather than scanning the NAS again.
It runs at 06:00 with up to 15 minutes of jitter, has independent retention/pruning, and verifies repository metadata after copying.
A failed local backup does not prevent it from copying earlier completed snapshots.

For example, add this to Glaciem's homelab options after arranging an SSH/SFTP account and writable directory on the friend's server:

```nix
backups.remote = {
  enable = true;
  repository = "sftp:backup@friend:/backups/glaciem";
  extraOptions = [
    "sftp.command='ssh -i /var/lib/restic/friend_ed25519 -o IdentitiesOnly=yes -o StrictHostKeyChecking=yes -o UserKnownHostsFile=/var/lib/restic/known_hosts backup@friend -s sftp'"
  ];
};
```

Provision the root-only private key separately and put the friend's verified SSH host key in `/var/lib/restic/known_hosts`.
The remote needs storage access, not your Restic password.
By default both repositories use your local sops-managed password;
a separate runtime `remote.passwordFile` can be supplied, including the path of another sops-nix secret.
The remote repository is initialized automatically.
Run `sudo systemctl start restic-backups-homelab-remote.service` to copy immediately.
This service does not trigger a new local backup; complete the first local backup before using it.
Large initial copies can also be seeded over a local network before moving the destination to the remote's home.

## Restore and verify

The generated `restic-homelab` and `restic-homelab-remote` wrappers select their repositories and credentials.
On a recovery machine, install Restic and supply `--repo` and `--password-file` explicitly instead.

```sh
sudo restic-homelab snapshots
sudo restic-homelab ls latest
sudo restic-homelab restore latest --target /tmp/homelab-restore
sudo restic-homelab check --read-data
```

Restored paths retain the ZFS snapshot layout, for example `/tmp/homelab-restore/fast/.zfs/snapshot/restic-homelab/...` and `/tmp/homelab-restore/var/.zfs/snapshot/restic-homelab/lib/...`.
Copy the contents back to their original live paths with the corresponding services stopped, preserving ownership and permissions.
Restore PostgreSQL's full data directory using the same PostgreSQL major version and required extensions;
these are physical database backups, not portable SQL exports.
Restore related application media and database directories from the same Restic snapshot.

Initially restore a small selection using `--include` and check its contents,
then test application recovery before relying on the backups.
Choose a restore target with adequate free space for larger restores.

## Implementation

Glaciem enables `homelab.backups`. The module is organized into:

| File | Purpose |
| --- | --- |
| [`backups/default.nix`](../dendritic/features/homelab/backups/default.nix) | Backup jobs and systemd integration |
| [`backups/_options.nix`](../dendritic/features/homelab/backups/_options.nix) | Public settings |
